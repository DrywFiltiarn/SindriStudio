## Analysis

### Prerequisites
- P1-A4 is COMPLETE (anvilml-core types are implemented and committed)
- `anvilml-ipc` crate exists with skeleton `lib.rs` and `Cargo.toml` (depends on `anvilml-core`, `serde`, `serde_json`)

### Protocol Reference
All message types and field names must match `docs/IPC_PROTOCOL.md` exactly. The protocol uses:
- **Transport**: stdin/stdout pipes (binary mode)
- **Framing**: 4-byte big-endian u32 length prefix + msgpack body
- **Serialization**: msgpack via `rmp-serde`
- **Discriminator**: `"type"` field (string) via `#[serde(tag = "type")]`
- **Max message size**: 64 MiB

### Existing anvilml-core Types Available
- `anvilml_core::types::job::JobSettings` — `{ dtype: DType, use_flash_attention: bool, vram_budget_mib: u64, allow_cpu_offload: bool }`
- `anvilml_core::types::model::DType` — `{ Float32, Float16, Bfloat16, Int8, Unknown }` (serializes to snake_case strings)
- `uuid::Uuid` — serialized as string per protocol spec

---

## Design Decisions

### 1. Shared vs. IPC-specific types
- **`JobSettings`**: Reuse `anvilml_core::types::job::JobSettings` directly. The field names and types match the IPC protocol exactly. `DType` serializes to snake_case strings (e.g., `"bfloat16"`), matching the protocol.
- **`DType`**: Reuse `anvilml_core::types::model::DType` directly in `PreloadModel`.
- **`device_type` in `Ready`**: Use `String` (not `DeviceType` enum). The protocol treats this as a free-form string value. Using `String` avoids serialization format mismatches and is simpler.
- **`graph` in `Execute`**: Use `serde_json::Value`. The protocol describes it as an "arbitrary workflow" map.

### 2. Enum serialization
Both `WorkerMessage` and `WorkerEvent` use `#[serde(tag = "type")]` for tagged/discriminated union serialization. This matches the protocol requirement that `"type"` is the discriminator key.

### 3. Framing generics
`write_message` and `read_message` are generic over `AsyncRead + Unpin` and `AsyncWrite + Unpin`, matching the protocol spec exactly. This allows them to work with `tokio::io::Stdin`, `tokio::io::Stdout`, `tokio::net::unix::pipe`, or any other async I/O source.

### 4. Error handling
- Use `anyhow::Result<()>` for framing functions (consistent with existing codebase patterns)
- `read_message` enforces the 64 MiB limit before allocating the buffer
- `rmp_serde` errors propagate through `anyhow`

#### 2c. Create `src/framing.rs`

```rust
use anyhow::{Result, ensure};
use serde::{Serialize, de::DeserializeOwned};
use tokio::io::{AsyncRead, AsyncWrite};

pub async fn write_message<W, T>(writer: &mut W, msg: &T) -> Result<()>
where
    W: AsyncWrite + Unpin,
    T: Serialize,
{
    let bytes = rmp_serde::to_vec_named(msg)?;
    let len = (bytes.len() as u32).to_be_bytes();
    writer.write_all(&len).await?;
    writer.write_all(&bytes).await?;
    Ok(())
}

pub async fn read_message<R, T>(reader: &mut R) -> Result<T>
where
    R: AsyncRead + Unpin,
    T: DeserializeOwned,
{
    let mut len_buf = [0u8; 4];
    reader.read_exact(&mut len_buf).await?;
    let len = u32::from_be_bytes(len_buf) as usize;
    ensure!(
        len <= 64 * 1024 * 1024,
        "message too large: {} bytes",
        len
    );
    let mut buf = vec![0u8; len];
    reader.read_exact(&mut buf).await?;
    Ok(rmp_serde::from_slice(&buf)?)
}
```
